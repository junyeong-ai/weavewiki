## 1. Executive Summary

### 1.1 문제 정의

현재 claudegen은 다음과 같은 근본적인 문제를 가지고 있습니다:

| 문제 | 현상 | 영향 |
|------|------|------|
| **형식 기반 품질 평가** | 파일 참조 개수, 키워드 존재 여부로 품질 판단 | 형식은 완벽하지만 무가치한 콘텐츠 통과 |
| **횟수 기반 수렴** | `max_iterations` 도달 시 강제 종료 | 품질 미달 상태로 완료 |
| **LLM 재작성 의존** | 모든 개선 전략이 LLM 호출에만 의존 | 근본 원인 해결 없이 반복 |
| **학습 시스템 미사용** | 패턴 학습 코드 존재하지만 미호출 | 동일 실패 반복 |

### 1.2 해결 방향

```
FROM: 형식 기반 → 횟수 기반 수렴 → 무가치 콘텐츠
TO:   가치 기반 → 품질 기반 수렴 → 고가치 콘텐츠
```

### 1.3 핵심 변경사항

1. **가치 중심 평가**: "AI가 이 정보 없이 실수할 수 있는가?"가 품질의 기준
2. **다차원 수렴 조건**: 형식 + 가치 + 교차검증 + 안정성 모두 충족 시 완료
3. **비즈니스/도메인 규칙 포함**: 코딩 규칙뿐 아니라 업무 규칙, 보안 정책, 성능 요구사항 등
4. **설정 기반 유연성**: 모든 임계치, 모델, 기준을 사용자가 제어

## 2. 핵심 가치 정의

### 2.1 claudegen의 존재 이유

```
┌─────────────────────────────────────────────────────────────────┐
│                    VALUE PROPOSITION                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  WITHOUT claudegen:                                             │
│  ─────────────────                                              │
│  • AI는 코드만 읽음 → 표면적 이해만 가능                        │
│  • 숨겨진 제약 모름 → 버그 유발 코드 생성                       │
│  • 비즈니스 규칙 모름 → 요구사항 위반                           │
│  • 도메인 지식 부족 → 부적절한 설계 결정                        │
│  • 결과: 반복적인 수정 요청, 낮은 품질                          │
│                                                                 │
│  WITH claudegen:                                                │
│  ────────────────                                               │
│  • AI는 핵심 제약 인지 → 버그 방지                              │
│  • 비즈니스 규칙 이해 → 요구사항 충족                           │
│  • 도메인 맥락 보유 → 적절한 설계 결정                          │
│  • 프로젝트 패턴 이해 → 일관된 코드                             │
│  • 결과: 첫 시도에 올바른 코드, 높은 품질                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 가치 공식

```
claudegen 가치 = f(실수 방지, 비발견성, 적합성)

실수 방지 (Mistake Prevention):
  - 이 정보가 없을 때 AI가 할 수 있는 실수의 심각도
  - 0.0: 실수 방지 안됨
  - 1.0: 치명적 실수 방지

비발견성 (Non-Discoverability):
  - 코드/문서만으로 이 정보를 발견할 수 있는 난이도
  - 0.0: 코드에 명시적으로 있음 (가치 낮음)
  - 1.0: 경험/히스토리로만 알 수 있음 (가치 높음)

적합성 (Artifact Fitness):
  - 해당 Artifact 유형(Rules/Skills/Agents/CLAUDE.md)에 맞는 정보인지
  - 0.0: 완전히 부적합
  - 1.0: 완벽히 적합
```

### 2.3 정보 유형별 가치

claudegen이 추출해야 하는 정보는 **코딩 규칙을 넘어** 다양한 유형을 포함합니다:

#### 2.3.1 기술적 제약 (Technical Constraints)

| 유형 | 설명 | 예시 |
|------|------|------|
| **리소스 공유** | 동시성 관련 제약 | "DB 연결 풀은 싱글톤으로 공유해야 함" |
| **초기화 순서** | 의존성 순서 제약 | "캐시 초기화 전에 설정 로드 필수" |
| **성능 제약** | Hot path, 메모리 제한 | "이 API는 100ms 이내 응답 필수" |
| **보안 제약** | 인증, 인가, 암호화 | "PII 데이터는 암호화 후 저장" |

#### 2.3.2 비즈니스/도메인 규칙 (Business/Domain Rules)

| 유형 | 설명 | 예시 |
|------|------|------|
| **업무 규칙** | 비즈니스 로직 제약 | "주문 취소는 배송 전에만 가능" |
| **규정 준수** | 법적/규제 요구사항 | "GDPR: 사용자 데이터 삭제 요청 30일 내 처리" |
| **도메인 불변조건** | 업계 표준 규칙 | "금융: 거래 금액은 소수점 2자리까지만" |
| **SLA 요구사항** | 서비스 수준 약정 | "결제 API 가용성 99.99%" |

#### 2.3.3 아키텍처 의도 (Architecture Intent)

| 유형 | 설명 | 예시 |
|------|------|------|
| **설계 결정** | 왜 이 구조를 선택했는지 | "이벤트 소싱 사용 이유: 감사 로그 요구사항" |
| **의도적 제한** | 의도적으로 지원하지 않는 것 | "멀티테넌시 미지원은 의도적 결정" |
| **마이그레이션 계획** | 변경 예정 사항 | "레거시 API는 Q3에 deprecated 예정" |
| **트레이드오프** | 선택의 이유와 대안 | "일관성 > 가용성 선택 (CAP theorem)" |

#### 2.3.4 암묵적 지식 (Tacit Knowledge)

| 유형 | 설명 | 예시 |
|------|------|------|
| **함정 (Gotchas)** | 비직관적인 동작 | "null 반환 시 호출자가 체크 안 함" |
| **역사적 맥락** | 왜 이렇게 되었는지 | "이 workaround는 외부 라이브러리 버그 때문" |
| **실패한 접근법** | 시도했다가 실패한 것 | "캐시 무효화 방식 A는 race condition 발생" |
| **팀 규칙** | 문서화되지 않은 관행 | "PR 리뷰어 최소 2명, 그 중 1명은 시니어" |

### 3.2 도메인별 고가치 정보 예시

#### E-Commerce 도메인

```yaml
business_rules:
  - "장바구니 상품 수량 변경 시 재고 실시간 확인 필수"
  - "쿠폰 중복 사용 금지, 단 VIP 등급은 2개까지 허용"
  - "해외 배송 주문은 관세 예상액 표시 필수"

technical_constraints:
  - "결제 트랜잭션은 분산 락 사용 (Redis SETNX)"
  - "상품 이미지 업로드는 비동기 처리 (큐 사용)"
  - "검색 인덱스 갱신은 배치로 처리 (실시간 X)"

gotchas:
  - "재고 차감은 결제 성공 후에만 (결제 실패 시 롤백 불필요)"
  - "할인가 계산 순서: 쿠폰 → 포인트 → 등급 할인"
```

### 5.1 CLAUDE.md

#### 목적
AI가 프로젝트를 "이해"하는 데 필요한 핵심 정보를 제공합니다. README와 다르게 **AI 관점에서 필요한 정보**에 집중합니다.

#### 포함해야 할 내용

| 섹션 | 설명 | 예시 |
|------|------|------|
| **Core Abstraction** | 프로젝트의 핵심 개념과 설계 철학 | "이 시스템은 이벤트 소싱 패턴으로 모든 상태 변경을 추적합니다" |
| **Critical Constraints** | 위반 시 버그/장애가 발생하는 필수 제약 | "DB 트랜잭션 내에서만 잔액 변경 가능" |
| **Architecture Intent** | 설계 결정의 이유와 트레이드오프 | "CAP에서 일관성 선택 - 금융 도메인 특성" |
| **Domain Context** | 비즈니스/도메인 핵심 규칙 | "환불은 결제 후 7일 이내만 가능" |
| **Gotchas** | 비직관적인 동작, 함정 | "이 API는 null 반환 가능 - 호출자가 체크 필수" |
| **Extension Points** | 확장/수정 시 알아야 할 것 | "새 결제 수단 추가: PaymentGateway 구현" |

#### 무가치 예시 vs 고가치 예시

```markdown
# 무가치 CLAUDE.md
─────────────────────────────
## Project Structure
- src/: Source code
- tests/: Test files
- docs/: Documentation

## Build
npm install
npm run build

## Test
npm test
```

```markdown
# 고가치 CLAUDE.md
─────────────────────────────
## Core Abstraction
이 결제 시스템의 핵심은 "멱등성 보장"입니다.
모든 결제 요청은 idempotency_key로 식별되며,
동일 키로 재요청 시 기존 결과를 반환합니다.

## Critical Constraints

### 트랜잭션 경계 (MUST)
잔액 변경, 거래 기록, 이벤트 발행은 반드시
단일 트랜잭션 내에서 수행해야 합니다.

```python
# CORRECT
with transaction():
    account.debit(amount)
    ledger.record(tx)
    events.publish(PaymentCompleted)

# WRONG - 부분 실패 시 불일치
account.debit(amount)
ledger.record(tx)  # 여기서 실패하면?
```

WHY: 부분 실패 시 잔액과 거래 기록 불일치 발생.
     복구 불가능한 상태가 됩니다.

### 환불 가능 조건
- 결제일로부터 7일 이내
- 부분 환불 불가 (전액만)
- 이미 정산된 거래는 환불 불가 (수동 처리 필요)

## Architecture Intent
이벤트 소싱을 사용하는 이유:
1. 금융 감사 요구사항 (모든 변경 추적)
2. 장애 시 이벤트 리플레이로 복구 가능
3. 비동기 알림 시스템과 자연스러운 통합

주의: 이벤트 스키마 변경 시 마이그레이션 필요
```

### 5.2 Rules

#### 목적
위반 시 버그/문제가 발생하는 **필수 제약**을 명시합니다.

#### Rule의 구조

```yaml
name: <간결한 식별자>
type: <technical | business | security | compliance>
constraint: <MUST | MUST_NOT | ALWAYS | NEVER>
what: <무엇을 해야/하지 말아야 하는가>
why: <왜 이것이 필요한가 - 위반 시 결과>
evidence:
  - <관련 코드/문서 위치>
example:
  correct: <올바른 예시>
  wrong: <잘못된 예시>
```

#### Rule 유형별 예시

**기술적 제약 (Technical)**
```yaml
name: transaction-boundary
type: technical
constraint: MUST
what: 잔액 변경, 거래 기록, 이벤트 발행은 단일 트랜잭션 내에서 수행
why: |
  부분 실패 시 데이터 불일치 발생.
  예: 잔액은 차감되었는데 거래 기록 실패 → 복구 불가능
evidence:
  - "@src/payment/service.py:45-67"
example:
  correct: |
    with transaction():
        account.debit(amount)
        ledger.record(tx)
  wrong: |
    account.debit(amount)
    ledger.record(tx)  # 트랜잭션 없음
```

**비즈니스 규칙 (Business)**
```yaml
name: refund-eligibility
type: business
constraint: MUST
what: 환불 처리 전 다음 조건 모두 확인 필수
  - 결제일로부터 7일 이내
  - 전액 환불만 가능 (부분 환불 불가)
  - 정산 전 거래만 자동 환불 가능
why: |
  비즈니스 정책 위반 시 재무 손실 발생.
  정산 후 환불은 수동 프로세스 필요 (회계팀 승인).
evidence:
  - "@docs/policies/refund-policy.md"
  - "@src/refund/validator.py:23-45"
```

**보안 제약 (Security)**
```yaml
name: pii-encryption
type: security
constraint: MUST
what: 개인식별정보(PII)는 저장 전 암호화 필수
  - 이름, 이메일, 전화번호, 주소
  - 카드번호, 계좌번호
why: |
  GDPR/개인정보보호법 위반.
  데이터 유출 시 법적 책임 및 벌금.
evidence:
  - "@src/encryption/pii_handler.py"
example:
  correct: "encrypted_email = encrypt(user.email)"

```

| 작업 | 설명 | 우선순위 |
|------|------|----------|
